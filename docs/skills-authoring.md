# プロジェクト skill の作り方

**読み手**: このプロジェクト固有の知識・規約・レビュー観点を skill にする人。

skill は、必要になった場面でだけ読まれる手順書。`AGENTS.md` が起動のたびに読み込まれるのに対し、skill は場面に応じて選ばれる。この差が置き場所を決める。

配布されている skill を導入して使う話は `docs/skills.md` にある。ここは**自分で書く**側の話。

## 書くのを助ける skill

skill を書く作業を支援する skill が既にある。ゼロから手で書く必要はない。

| skill | 何をするか | 使える場所 |
| --- | --- | --- |
| `/writing-for-agents` | エージェントが読む文書の書き方。`SKILL-MECHANICS.md` に frontmatter と起動方式の詳細がある | 導入していれば Claude Code と Copilot の両方 |
| `skill-creator` | 対話で skill を作り、テストケースを回して `description` の当たり方を測る | **Claude Code のみ。** Anthropic 公式プラグインで、別途有効化が必要 |

**この文書が決めるのは、このプロジェクトでの置き場所と切り分け。** 書き方そのものは `/writing-for-agents` のほうが詳しい。食い違ったときは、置き場所と切り分けはこの文書、文章の書き方は `/writing-for-agents` に従う。

## まず「skill にすべきか」を決める

skill にしないほうがよいものが多い。書きたい内容ごとに置き場所は決まっている。

| 書きたいこと | 置き場所 |
| --- | --- |
| 語の定義。「注文」とは何か | `CONTEXT.md` |
| 決定とその理由。なぜその設計を選んだか | `docs/adr/` |
| **常に**効く短い規約。言語、コミット形式、禁止事項 | `AGENTS.md` |
| **特定の場面でだけ**必要な手順・観点 | プロジェクト skill |
| 調査中のメモ | `.scratch/` |

判断の軸は 2 つ。

- **定義か、手順か。**「それが何であるか」は `CONTEXT.md`、「どう扱うか」は skill
- **常にか、場面によるか。** 常に効くなら `AGENTS.md`、場面によるなら skill

`AGENTS.md` が長くなってきたときが切り出しの合図。常時読み込まれるファイルが膨らむと、本当に守ってほしい制約が埋もれる。

### 消しても挙動が変わらない行は削る

書いたら 1 行ずつ問う。**「この行を消したら、エージェントの動きが変わるか。」** 変わらないなら削る。Anthropic が指示ファイルについて示している基準で、skill にも同じことが言える。

削る対象として名指しされているもの。

- **リポジトリを読めば分かること。** ディレクトリ構成、技術スタックの一覧、設定ファイルに書いてあるコマンド
- **既定で守られること。** モデルが指示されなくても行うことを書いても、負荷を払うだけで何も変わらない

ただし**例外が 2 つある。方針と落とし穴は、最近破られていなくても残す。** 「守られているから要らない」は削除の根拠にならない。守っている対象そのものが無くなったときにだけ消す。

### 用語と決定を skill に書き写さない

skill から `CONTEXT.md` や `docs/adr/` を**参照する**のはよい。**書き写す**と、片方を更新したときにもう片方が古くなり、どちらが正典か分からなくなる。

```markdown
（避ける）
## 用語
注文とは、顧客が商品の購入を確定させた記録である。

（こうする）
用語は `CONTEXT.md` に従う。この手順は「注文」「請求」を既知として扱う。
```

## 置き場所

```
.claude/skills/<skill 名>/SKILL.md
```

`.claude/skills/` を使うのは、**Claude Code と GitHub Copilot の両方が読む唯一の場所**だから。Copilot では `copilot skill list` の Project skills として並ぶ。`.github/skills/` は Copilot にしか届かず、`~/.agents/skills/` は個人 skill なので他の参加者には配られない。

- **コミットする。** clone した全員に配られることが目的
- **CI の検査対象に入る。** GitHub を使う場合、`.github/workflows/security.yml` はリポジトリ全体を走査するので、ここに置いた skill は自動的に SkillSpector にかかる
- `.claude/settings.local.json` は個人設定なので `.gitignore` してある。skill だけがコミットされる

## SKILL.md の書式

```markdown
---
name: order-cancellation
description: 注文の取り消し手順。取り消し、返金、キャンセル料に関わるコードを変更するときに使う。
---

（本文）
```

frontmatter で使うキーは 4 つ。導入元である mattpocock/skills の 35 件での使用状況を併記する。

| キー | 必須 | 使用 | 内容 |
| --- | --- | --- | --- |
| `name` | 必須 | 35/35 | 小文字・数字・ハイフンのみ。**ディレクトリ名と一致させる**（35/35 で一致している） |
| `description` | 必須 | 35/35 | いつ使うか。後述 |
| `disable-model-invocation` | 任意 | 20/35 | `true` にすると自動起動しなくなる。後述 |
| `argument-hint` | 任意 | 4/35 | 明示的に呼ぶときの引数の説明 |

本文の長さは 35 件の中央値で約 3300 文字。Agent Skills の仕様は `SKILL.md` 本体を **5,000 トークン未満**に収めるよう求めている。大きく超えるなら補助ファイルに分けて `SKILL.md` からリンクする（10/35 がそうしている）。

**参照は 1 階層まで。** `SKILL.md` → `詳細.md` はよいが、`詳細.md` からさらに別のファイルを参照させない。参照先から参照されたファイルは、冒頭だけ読まれて全文が読まれないことがある。

### description が起動を決める

**エージェントは本文を読まずに `description` だけで、その skill を使うかどうかを判断する。** ここが弱いと、正しく書かれた skill が一度も呼ばれない。

「何をするか」ではなく「**いつ使うか**」を書く。

```
（起動しない）
description: API のレビュー用

（起動する）
description: 公開 API の後方互換性を確認する。エンドポイントのシグネチャ、
  レスポンスの形、エラーコードを変える変更をレビューするときに使う。
```

35 件の `description` は中央値 149 文字（最短 51、最長 418）。1 行に収めようとしなくてよい。

### 自動起動にするか、明示呼び出しにするか

**自動起動は無料ではない。** `disable-model-invocation` を省略すると `description` が常時読み込まれ、エージェントが自分で起動を判断できるようになる。その代わり、書いた分だけ context を恒久的に占める。`true` にすると `description` は読み込まれなくなって負荷はゼロになるが、**人間が名前を覚えていない限り二度と呼ばれない。**

判断の軸は 1 つ。**エージェントが自分で辿り着く必要があるか。**

| | 該当する skill |
| --- | --- |
| 自動起動（省略） | `code-review` `tdd` `domain-modeling` `diagnosing-bugs` `git-guardrails-claude-code` |
| 明示呼び出しのみ（`true`） | `to-tickets` `triage` `handoff` `wayfinder` `setup-matt-pocock-skills` |

起票やセットアップのように人間が「今からこれをやる」と宣言するものは `true` でよい。人間が呼ぶのだから、エージェントが見つけられる必要がない。

**この文書が扱う 3 つの型は、いずれも自動起動にする。** ドメイン手順も規約もレビュー観点も、該当するコードを触るときに効かなければ意味がなく、そのとき人間は skill の存在を思い出さない。context を払う価値がある側。

`true` にした場合、`description` は**人間向けの 1 行**になる。エージェントは読まないので、起動条件を書き込んでも効果がない。

起動方式のより詳しい説明は `/writing-for-agents` の `SKILL-MECHANICS.md` にある。

## 3 つの型

### ドメイン知識

「この領域ではこう扱う」という手順。用語の定義は `CONTEXT.md` に置き、skill は手順だけを持つ。

- 名前は扱う対象で付ける（`order-cancellation`、`billing-proration`）
- 自動起動にする
- `description` には**その領域のコードを触るとき**と書く。ドメイン名だけでは起動の判断に使えない

### 独自ルール

`AGENTS.md` に書くには長すぎる規約。

- `AGENTS.md` には 1 行だけ残し、詳細を skill に置く形にできる
- 自動起動にする。違反しそうな場面で効かなければ意味がない
- **守れないときにどうするかを書く。** 禁止だけを書いた規約は、守れない状況に出会ったときに黙って無視される

### レビュー観点

`/code-review` だけでは見落とす、このプロジェクト固有の観点。

- `/code-review` 自体が自動起動なので、観点 skill も自動起動にすれば同じ場面で一緒に効く
- **何を見るかを列挙する。** 「丁寧にレビューする」では動作が変わらない
- 見つけたときの扱い（変更を止めるのか、指摘に留めるのか）まで書く

## CI がどう検査するか

GitHub を使う場合、`.claude/skills/` に置いた skill はリポジトリ全体の走査に含まれる。SkillSpector が `SKILL.md` を解析対象のひとつとして読み、危険な指示や秘密の混入を検出する。

**検出されたら、まず本当に問題が無いかを疑うこと。** skill はエージェントが従う指示そのものなので、誤検知として片付ける前に内容を確認する。

検出されやすい書き方。

- 外部から取得したスクリプトを、検証せずそのまま実行させる手順
- 描画すると見えなくなる場所に書かれた指示。HTML コメントなど
- 認証情報らしき文字列。例示のつもりで書いたトークンも含む
